# Fayda — Decisions

Status as of 30 Oct 2026. **Approved** = founder decided. **Implemented, awaiting confirmation** = built in the prototype, but the founder hasn't explicitly confirmed it. **Provisional** = a placeholder value. **Open** = not decided.

## Product model

| # | Decision | Status |
|---|---|---|
| D1 | Working name **Fayda**. Brand, domain and package ids are not final. | Open (B1) |

## Bargaining

| # | Decision | Status |
|---|---|---|
| B-1 | Listing modes are **two**: **Buy now only** (`BUY_NOW`, fixed price) and **Buy now + offers** (`BOTH`). Bargaining is always private: there is no public bargaining and no "bargaining only" mode. Supersedes the earlier Fixed / Private / Public / Both. | Approved (founder, 31 Oct 2026) |
| B-2 | Private rules per listing: **lowest price accepted automatically** (A), optional **auto-counter price** (C ≥ A), optional **auto-decline below** (D < A). | Approved |
| B-3 | **Auto-counter fires 5 s after every buyer offer below A.** The buyer sees it as the seller's own counter (no "automatic" label). It never goes higher than the seller's last counter. It stops at the 6-offer limit. | Approved |
| B-4 | Auto-decline is delayed by 2 minutes, to stop buyers probing the seller's floor. | Provisional |
| B-5 | Turn-taking with counters that must converge: a buyer's counter must go up and stay below the seller's counter; a seller's counter must go down and stay above the buyer's offer. | Approved |
| B-6 | Website listings: an automatic accept settles at **A (the code's price)**, even if the buyer offered more. | Implemented, awaiting confirmation |
| B-7 | Hide "automatic" from buyers for automatic **accepts and declines** too. Buyers get no information at all that any reply was automatic. | Approved (31 Oct 2026) |

| I-39 | **M3.9 Search and ranking (founder, 1 Nov 2026; plan approved, weights to be tuned on test data).** **Search:** each word must match; it is the word itself (full points), a synonym or plural (80%), or a close misspelling by `pg_trgm` word similarity ≥ 0.55 on words of 4+ letters (60%), in title (40), tags (30), category (25), shop name or handle (20) or description (10; never fuzzy). Synonym groups are in `packages/domain/src/search.ts`. Results are ordered by relevance, then the For You score. **Deviation from the plan:** no `tsvector` column; substring and trigram matching cover the spelling and synonym goals, and a generated column across `listings` and `sellers` adds migration risk for no gain at this size. GIN trigram indexes exist on title and description; tags and shop name are still scanned (known limit, fine for thousands of listings). **For You:** a stored integer score `listings.rank_score` (0 to 9999) refreshed every 5 minutes by the sweep (`rankScore` in `packages/domain/src/ranking.ts`: recency with 96 h half-life up to 3000, likes up to 1800, views 30 d up to 1000, the shop's delivered share up to 1000 plus fast-confirm bonus, in stock 300, new listing and new shop head starts, sold out cut to 10%), plus a per-buyer follow boost of 1500 added at request time. **Saves are not an input** (I-28). The sort `BEST` is the new default (best match when searching, For You score otherwise); `NEWEST` stays strictly newest; Following and shop pages stay newest first. `FEED_RANKER=newest` switches For You back to newest-first with no code change. A page marker holds the rank key; a refresh between two page fetches can repeat or skip a listing (accepted). Weights are provisional. **ML groundwork:** `feed_impressions` (buyer, listing, position, scope, ranker; pruned after 90 days; capped 1000 an hour per buyer); the page tells the app which `ranker` ordered it. Later ML options (pgvector embeddings, learned weights, bandits) are in the 1 Nov 2026 discussion and need founder approval per library. | Proposed |
| I-40 | **App and server version check (founder, 1 Nov 2026).** The contracts carry a `CONTRACT_LEVEL` (a whole number; **raise it by one whenever a request or response changes in a way an older app cannot handle**: a new required field, a rename, a removed route; currently 2). Each app is built with the level of the contracts it was built from and sends `X-Client-App` and `X-Client-Level` on every request. `/v1/meta` reports `apiLevel` (the server's level) and `minClientLevel` per app (set with `MIN_CLIENT_LEVEL_BUYER` and `MIN_CLIENT_LEVEL_SELLER`, default 1). An app below its minimum gets **426 `CLIENT_TOO_OLD`** (health, meta and the API description are exempt, so the app can still explain); a request with no header, or one that cannot be read, is let through (a browser, a script, an app from before this check). On start each app reads `/v1/meta` and shows a blocking "Please update" screen when it is below the minimum, or a quiet note when it is newer than the server (an old server that reports no levels counts as level 1).
